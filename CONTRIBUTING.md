# Contributing to Vibe Studio

Three rules come before everything else:

1. No client data, secrets or credentials in source, tests, examples or screenshots. Use fictional, licensed fixtures.
2. Keep the application standalone: no required sibling kit checkout, developer-specific path or real user profile in tests.
3. Validate behaviour, not assumptions. Preserve deployed kit contracts and existing user data.

## Repository layout

| Path | Content |
| --- | --- |
| `app/` | Electron main process, preload, desktop interface and local user preferences |
| `core/` | Project controller, Python bridge, guards, journal and shared interface modules |
| `core/adapters/` | Copilot, Claude Code, Codex and Gemini harness adapters |
| `core/schema/vibe-studio.schema.json` | Vibe Studio's public protocol-2 contract schema, implemented independently by kits |
| `test/` | Node and Python regressions with fake harnesses |
| `test/fixtures/` | Licensed protocol-2 reference-kit snapshots, excluded from the portable application |
| `scripts/` | Portable/Windows installer packaging and isolated Electron smoke checks |
| `docs/` | Contract and kit-authoring documentation |
| `.github/instructions/` | Versioned contributor instructions for coding agents; not generated by APM |

Do not edit generated `node_modules/`, `dist/` or Python caches. GitHub Actions in `.github/workflows/ci.yml` is the repository's CI. Keep its Linux/Windows regressions and Windows distribution checks aligned with the commands below.

Keep test source files and the fictional, licensed `test/fixtures/` under version control: CI needs them. Generated projects/profiles (`.test-*` and `.profile-test-*` at the repository root), Python caches, distributions and npm debug logs are ignored. Tests normally clean their temporary workspaces; the ignore rules also cover interrupted runs. Never ignore all JSON, YAML, Markdown or image files, since fixtures and application assets use those formats.

For retained Electron screenshots and diagnostics, set `VIBE_STUDIO_SMOKE_ARTIFACTS` to `dist\test-artifacts` before `npm run test:smoke`. Installer UI captures already default to `dist\installer-ui`. Do not choose a source/fixture folder as the output location. Inspect retained logs and captures before sharing them: even fictional tests can record local workstation paths. An ignore rule does not remove an already tracked file or erase its Git history.

## Setup

Requirements: Node.js 22.12+ and Python 3.11+. CI uses Node.js 24 and Python 3.12.

```powershell
npm ci
python -m pip install -r requirements.txt
npm start
```

Development can use an isolated profile instead of the existing `%APPDATA%\Vibe Studio` profile:

```powershell
npm start -- --user-data-dir="C:\Temp\vibe-studio-profile"
```

See `README.md` for harness installation and sign-in. A real AI session is not required for the automated checks.

## Before a pull request

Run the smallest checks covering the change. Before a release or a change affecting several application surfaces, run:

```powershell
npm test
npm run test:bridge
npm run test:smoke
npm run package
npm run test:portable
```

For Windows installer changes, also run `npm run installer:tools`, `npm run package:installer` and `npm run test:installer` on Windows x64. The compiler lives in the ignored `dist\installer-cache` folder. The installer smoke has its own installation identity and disables shortcuts; never run it against an existing installation or user profile. Keep the GitHub Actions workflow consistent. See `README.md` for build-time Python overrides, offline-base behaviour and optional-tool limitations.

For wizard changes, run the opt-in `npm run test:installer:ui` on an interactive Windows desktop and inspect its French/English window captures. Check light/dark variants without changing the user's Windows settings; see the compiler override in `README.md`. Keep native keyboard and high-contrast behavior. Wizard assets are generated from the existing logo, never edited in `dist`.

The packaging and portable commands above target the current platform; the Windows distribution must be checked on Windows. Close running portable processes before packaging or replacing their folder. The packaging script refuses to overwrite an executable in use.

Smoke checks use fake harnesses and temporary profiles: never point them at a real user profile. Kit checks use the bundled reference fixtures, not another repository. Documentation-only changes need no application test run unless they change an executable example.

Changes to model policies, catalog caching or context controls must cover first use without a cache,
account isolation, explicit selection validation and actual session settings with fake harnesses. Unit catalog
providers run from installed kit skills with a read-only JSON interface; test missing/invalid specifications,
non-contiguous IDs, dependencies and unchanged project files. Keep kit-specific parsers in their own repositories.
The portable smoke checks the embedded/window Windows icons and updates a disposable stale shortcut, never
the user's real Start menu. Do not delete the Windows icon cache or restart Explorer during validation.

## Typical changes

1. For interface changes, preserve the existing design and update English and French messages in `core/i18n.mjs`. Check the relevant interaction in Electron, including narrow-window behaviour.
2. For harness changes, extend the corresponding fake-client or fake-protocol tests. Keep guard refusals, explicit guard confirmations and the distinction between Approve All and Autopilot.
3. For contract changes, update the application's public schema, documentation and reference fixtures together. Preserve `vibe-studio.json`, protocol identifiers, report tools, MCP namespaces and journal compatibility unless a breaking change is explicitly planned.
4. For profile changes, preserve preferences, recent projects, approvals and step journals. Test with temporary copies, never the real `%APPDATA%\Vibe Studio` profile.
5. For fixture changes, retain licence and provenance information in `test/fixtures/README.md`. Kit-owned scripts remain fixtures, not application runtime implementations.
6. For dependency or packaging changes, update the relevant lockfile, check the generated distributions and review redistribution terms. Installer Python wheels are pinned with hashes in `scripts\installer\requirements.txt`; optional archives are pinned in `scripts\installer\components.json`; Gemini has its own npm lockfile. Do not bundle the proprietary Claude Code executable or publish a release as part of an ordinary change.

## Commits

Coding agents follow the same commit, changelog and release rules through `.github/instructions/changelog-and-commits.instructions.md`. Keep these sections in sync in both files.

1. Commit messages are always in English. Use `<type>(<scope>): <summary>`; the scope is optional. Types: `feat`, `fix`, `docs`, `refactor`, `test`, `ci`, `chore`, `release`.
2. Scope: the application component changed, for example `app`, `core`, `copilot`, `claude`, `codex`, `gemini`, `packaging` or `docs`. Omit it for an application-wide change.
3. Summary: imperative mood, lower case first word, no final period, 72 characters at most for the whole subject line.
4. Body after a blank line: explain why the change is needed and what the user sees. Wrap at 72 characters.
5. One logical change per commit. Before committing, read `git --no-pager log --oneline -10` and match the existing style; an empty repository has no history to match.
6. A commit written with an AI agent ends with the required `Co-authored-by:` trailer naming the agent.
7. Never commit client data, secrets, tokens, user profiles or generated portable artifacts. Never amend a pushed commit, force push, or move or delete a published tag.
8. Only commit, amend, push, tag or publish when the user explicitly asks for that operation. A request to change code is not permission to commit or release.

Examples:

```text
feat(app): attach images to a conversation
fix(gemini): preserve explicit guard confirmations
docs: explain isolated profile selection
release: vibe-studio 0.4.0
```

## Changelog

1. `CHANGELOG.md` is always in English.
2. Every change visible to application users or contributors gets an item under `## Unreleased` at the top, in the same change as the implementation or documentation.
3. Version heading: `## X.Y.Z`, without a date. The tag carries the date.
4. Subsections, in this order, only when non-empty: `### Added`, `### Changed`, `### Changed (breaking)`, `### Deprecated`, `### Removed`, `### Fixed`, `### Security`, `### Migration from X.Y`.
5. Numbered lists, one change per item, starting with the component in backticks and a colon, for example `` `app`: `` or `` `contributing`: ``.
6. Describe the effect for the user or contributor, not implementation details. Use the present tense.
7. When the application version changes, name it in the item as `Vibe Studio X.Y.Z`. Application versions are independent of kit release numbers.
8. A breaking change goes under `Changed (breaking)` and includes a `Migration from X.Y` subsection, including contract or profile migration instructions when applicable.
9. Do not rewrite published entries, except to fix their format.

## Releases

1. Only release when the user explicitly asks. State the chosen version and why; committing, tagging, pushing and publishing still require the corresponding user authorisation.
2. Use Semantic Versioning. Before 1.0.0, a feature or breaking change raises the minor version; a fix or compatible adjustment raises the patch version. Do not bump a version for an unrelated edit.
3. Rename `## Unreleased` to `## X.Y.Z` in `CHANGELOG.md`. Update the application version in `package.json` and `package-lock.json` together, including the root package entry of the lockfile. Update current-version assertions or examples where needed; preserve historical release and provenance text. Do not change kit versions or protocol versions as a side effect.
4. Run the full checks listed in "Before a pull request", including Windows packaging and the real portable smoke. Verify the executable metadata, ZIP contents and preservation of user data. Recheck bundled dependency licences before distribution.
5. If a release commit is requested, use `release: vibe-studio X.Y.Z`. Keep it limited to the version change, release heading and directly related release metadata.
6. If a tag is requested, create annotated tag `vX.Y.Z` with message `Vibe Studio X.Y.Z`. If a push is requested, use the confirmed remote and branch of this application. Check that the remote branch and tag point to the release commit. Publishing the portable is a separate, explicit operation; never move a published tag.

## Language

Source documentation, canonical labels, copy examples, design previews, commit messages and changelog entries are written in English. Desktop interface messages are maintained in both English and French in `core/i18n.mjs`; kit-provided translations stay in their contracts. Preserve explicit locale dictionaries, French-locale assertions, historical reference fixtures and multilingual input parsers. Do not translate or rename historical protocol identifiers or on-disk compatibility paths just to match the product name.
